USB/RF/OLED-компонентами дока и мыши. Новый разбор и ещё не решённые аппаратные

## Каталог обновлений

Renderer выполняет POST `https://api2.rongyuan.tech:3816/api/v2/get_fw_version` с JSON `{"dev_id":1755}` либо1759. Запросы21 октября для обоих точных ID дали HTTP500 / `Record not found`. Ограниченная проверка явно перечисленных в том же renderer родственников1754/1852/2349/2350 дала тот же результат. Широкого перебора ID не было.

Это означает отсутствие полученной записи каталога в данном запросе. Это **не** доказательство последней установленной версии, отсутствия обновлений у производителя или отсутствия любых иных серверов. Имя файла из отрицательного ответа не получить.

Успешный ответ каталога должен содержать `file_path`; загрузка выполняется из `/download/<file_path>`. Общий декодер различает ZIP и raw DEFLATE, в ZIP ищет `firmwareFile.bin`, `firmwareRFFile.bin`, `firmwareOledFile.bin`, `firmwareMledFile.bin`, `firmwareNordicFile.bin`, `firmwareFlashFile.bin`. Наличие этих имён в общем коде не означает, что для нашего комплекта опубликованы все шесть компонентов.

## Реальная привязка классов и обновление

Фабрика сопоставляет `mouse_pan1080_g62_screen_1k_8k` классу `_ra`, наследующему `z9r`. Это профиль ID1755. Унаследованная `upgrade` выбирает исполняемую часть входного файла со смещения0x10000 и передаёт её64-байтовыми частями, со стартом BA/C0 и завершением BA/C2 с24-битной суммой. Перед этим функция посылает команду смены режима и ожидает загрузчик.

Этот разбор **не устанавливает** физический адрес назначения, карту flash или MCU: смещение во входном файле не равно доказанному адресу памяти. Другой обработчик `upgrade_dev` имеет USB-смещение0x5000 и RF0x10000, но он принадлежит другому классу. Его нельзя выбирать для1755 из-за похожего имени модели. Недостаточная проверка ACK в штатном коде не переносится в наше приложение.

Фабрика сопоставляет `common_dangle` классу `qpa`. Именно этот профиль объявлен для ID1759. В нём:

- `getOLEDversion` читает AD и возвращает OLED/flash version;
- `getFirmwareVersion` возвращает undefined;
- `upgrade` возвращает false;
- `setLightSetting` возвращает false, `getLightSetting` — undefined;
- передача изображения/анимации экрана и установка часов реализованы отдельно и уже перенесены в Rust.

Поэтому кнопка обновления в универсальном интерфейсе сама по себе не доказывает рабочий обновлятор этого дока. В других классах найдены OLED/MLED-upgrade обработчики, но соответствие контроллеру нашего дока не установлено. Их команды на устройство не отправлялись.

Имена профилей содержат PAN1080, но маркировка физического MCU не прочитана. Предположение по имени класса не заменяет идентификацию платы.

## Чтение без изменения firmware

CLI `ajazz-lab mouse-firmware-info [REPORT.json]` и кнопка в «Диагностика и прошивки» работают через существующую службу AJAZZ, без открытия конкурирующего HID-handle. Разрешены только AD дока и8F/80 мыши. Идентичность мыши проверяется до чтения версии и после него; пустой/чужой ответ не становится версией. Радиопредставление0x800006DB не принимается вместо ответа8F сID1755. При сне отчёт сохраняет OLED и отдельную ошибку мыши; кеш службы не объявляется физическим подтверждением ID.

Содержимое64-байтовых ответов и время чтения доступны в JSON. Нулевое поле flash version не трактуется как объём памяти. Эти ответы содержат метаданные, а не содержимое flash.

Первый аппаратный запрос через службу подтвердил AD04010000… / OLEDV104; на запросы мыши служба ответила `dev is not online`. После физического пробуждения мыши пользователем получены настоящий ID1755 и ответ GET80 `80 02 03`: raw version0x0302. ID повторно проверен после чтения версии; ошибки отсутствуют. Доказательство: `research/local/mouse-firmware-20261021/rust-service-identity-awake.json`. Это версия, не дамп кода.

## Что необходимо для кастомного кода

Нужны точные стоковые образы мыши ID1755 и дока ID1759, соответствие отдельных RF/OLED компонентов, карта MCU/PCB/памяти, границы загрузчика, уникальные данные сопряжения и калибровок, условия проверки образа и реально доступное восстановление. ## Дополнительный разбор USB, SDK и настоящих образов

После подключения мыши кабелем появился собственный интерфейс `3151:4026`. Через него повторно прочитаны ID1755 и версия `0x0302`, с проверкой ID до и после чтения. Настройки не записывались. Ответы: `research/local/mouse-firmware-20261021/wired-get-proof.json`.

У мыши и дока исследованы все доступные HID-коллекции через Windows HID parser, с desired access 0, без отправки отчётов. Для настройки они объявляют Feature Report ID0, usage page FFFF / usage2, длина65 с нулевым служебным байтом Windows. Report ID0A из публичного протокола Panchip не объявлен. Полный снимок: `hid-report-capabilities.json` в каталоге исследования. Это описание текущего режима, не доказательство содержимого недоступного загрузчика.

Получены официальные справочные SDK Panchip 0.8.0 и1.3.1 (только индекс и выбранные исходники через HTTP Range). Изучены стандартный Zephyr USB DFU, частный USB DFU и SPI DFU. Стандартный `usb_dfu.c` содержит DFU_UPLOAD / flash_area_read, однако такой интерфейс на подключённых устройствах не обнаружен. Частный протокол использует Report ID0A; его исходники USB/SPI DFU содержат обновление и метаданные, но не команду выгрузки всей flash. Он отличается от BA/C0 протокола штатного обновлятора AJAZZ. Наличие этих механизмов в SDK не доказывает их включение в нашей плате.

Первоисточники: [Panchip SDK](https://wiki.panchip.com/ble/pan1080_series/), [USB-протокол](https://docs.panchip.com/pan1080dk-doc/latest/docs-zdk/04_dev_guides/panchip_usb_protocol.html), [DFU](https://docs.panchip.com/pan1080dk-doc/latest/docs-zdk/04_dev_guides/zephyr_dfu_guidance.html). Полученные C-файлы и индексы находятся в `research/vendor/panchip-reference/`.

Мышь из комплекта AJ179 содержит ID1852 в инициализации persistent settings, из комплекта AJ159 PRO — ID1754. ID1755 в этих местах отсутствует. В образе мыши AJ179 USB descriptor3151:4026 / bcd0303, в приёмнике PAN1080 normal USB4027 / boot4029; это не отдельный образ OLEDV104 и не доказательство полного кода USB-дока5007. Карта относится к найденным файлам, а не автоматически к подключённым платам.

У мышиного справочного загрузчика функция0xCEC разбирает WORD0xFFBA /0xC0BA /0xC2BA: handshake, начало приёма и финальную проверку. BA/FF возвращает четыре байта из фиксированного адреса0xF004 через flash driver. Адрес не берётся из пакета; это не произвольное чтение flash. Команда C0 включает состояние приёма/записи, C2 возвращает результат суммы/проверки. Дамп не получен, переход в загрузчик и его команды на физические устройства не выполнялись. Дизассемблирование: `reference-mouse-boot-dispatch.asm`. Прежние кандидаты сравнения с0x8F оказались работой с сенсором, а не найденным USB-диспетчером.

Воспроизводимое извлечение и проверка: `tools/extract_ry_reference_firmware.py`. Пять offline-регрессионных проверок (`tools/test_reference_firmware.py`) подтверждают валидные подписи и отказ при изменении кода/подписи, усечении и повреждении TLV. Эти проверки не являются аппаратной проверкой кастомной прошивки.

Декомпиляция основного кода в Ghidra завершена: экспортированы1082 функции мыши и505 функций приёмника. Проект, C-представление и журналы сохранены в `research/local/mouse-firmware-20261021/ghidra/`. Это результат декомпилятора, а не восстановленные оригинальные исходники или проверенная новая прошивка. Официальные portable Ghidra12.1.4 и Temurin21 проверены по опубликованным SHA-256 и распакованы только в `.tools`; глобальная установка Java не выполнялась.

Дальнейшие проверки ограничены доступными USB-интерфейсами и полученными файлами; запрашивать повторно разборку не требуется. Полная кастомная прошивка остаётся незавершённой: точного образа ID1755/OLEDV104, схемы платы и подтверждённого восстановления пока нет.

### Найден настоящий диспетчер USB

В справочной мыши AJ179 функция `0x36A50` разбирает64-байтовый запрос из `0x200053EC`. Таблица команд `0..0x55` находится по адресу `0x53288`, таблица `0x7F..0xEF` — `0x530C4`. Проверены все86 и113 записей. Вторая таблица содержит переход в загрузчик по `7F`: старший бит команды сам по себе **не означает безопасное чтение**.

Изолированное исполнение исходных инструкций в Unicorn подтвердило GET80 → `03 03`, GET8F → ID1852 / wired mode6, а также расположение полей GETD3. Фоновые функции обслуживания подменены; RAM синтетическая, flash защищена от записи, USB и MMIO отсутствуют. Это проверка отдельных обработчиков, не эмуляция полностью работающей мыши. Физическая мышь1755 по-прежнему имеет другую версию0x0302.

Обработчики чтения flash ограничены следующими выражениями:

| Команда | Адрес источника в справочном коде | Условие копирования |
|---|---|---|
|96|`0x70000 + u8(request[1])*256 + u8(request[2])*64`|`request[2] < 5`|
|D0|`0x6E000 + u8(request[1])*256 + u8(settings[0x16])*64`|64 байта|
|D1|`0x6F000 + u8(request[1])*64`|`request[2] <= 1`|
|EF|Внешняя SPI flash, фиксированные8 байт по0xE000|Проверка инверсных байтов производственных метаданных|

Для96/D0/D1 минимальный адрес0x6E000, максимальный0x81EC0; длина64 байта. Исполняемая часть приложения найденного образа заканчивается до0x59834. Граничные значения проверены **только в эмуляторе**. Эти обработчики не дают выгрузить код; они не доказывают отсутствие любых иных интерфейсов в других ревизиях или ROM. Произвольные запросы за пределами валидных профилей на физическую мышь не отправлялись.

Справочный приёмник имеет другой диспетчер `0x31FD8`, маркер конверта44 и13 записей таблицы BB..C7 по0x39AD0. Этот протокол нельзя напрямую выдавать за USB-команды дока5007: код приёмника и отдельного контроллера USB/экрана должны быть сопоставлены. Отдельный код OLEDV104 из полученных пакетов не извлечён.

Воспроизведение без устройств:

```powershell
python tools/audit_mouse_reference_dispatch.py
python tools/emulate_mouse_reference_gets.py
python -m unittest discover -s tools -p test_reference_firmware.py
```

Нужны зависимости из `tools/requirements-firmware.txt` и сохранённые справочные файлы. Результаты: `reference-command-audit.json`, `reference-mouse-dispatch-audited.asm`, `reference-receiver-dispatch-audited.asm`, `emulated-reference-gets.json` в каталоге исследования.

### Ключ подписи и актуальный веб-драйвер

Открытый RSA-ключ справочных загрузчиков имеет SHA-256 `fc5701dc6135e1323847bdc40f04d2e5bee5833b23c29f93593d00018cfa9994`. Он **совпадает с открытой частью публичного тестового ключа** из [MCUboot root-rsa-2048.pem](https://github.com/mcu-tools/mcuboot/blob/main/root-rsa-2048.pem). Следовательно, подпись найденных файлов не подтверждает авторство AJAZZ и для этих справочных образов не является непреодолимым барьером модификации. Совпадение ключа с физическими загрузчиками1755/1759 пока не установлено.

Повторно получен актуальный скрипт [qmk.top](https://qmk.top/) `js/index.DBxGlqV7.js`:3612926 байт, SHA-256 `8a15096047a5c395520564cfd9f065f5fd896dad085ae7700522cd87caf740b8`. ### Уточнение устройства дока

В `support_config.json` найденного обновлятора именно USB3151:5007 сопоставлен методам `DANGLE4K`, `DANGLE4KRF`, `OLED`, `MLED`, `FLASH`, `TOUCHSCREEN`. PID4027 сопоставлен `DANGLE1K`. Это общий список возможностей программы, не подтверждение пригодности каждого образа.

У радиокомпонента и внешнего USB/экранного контроллера могут быть разные PID. Поэтому наличие4027 внутри PAN1080-образа **само по себе не исключает** его применение как радиокомпонента дока5007; оно также не доказывает совместимость с1759. Отдельный образ OLEDV104 по-прежнему не выделен.

Статический анализ PE обновлятора дал девять функций-кандидатов по ссылкам на `dangle4k.rs`, `oled.rs`, `mled.rs`; шесть экспортированы в C-представление. Общий автоматический анализ PE достиг лимита180 секунд, поэтому он не считается полным. Выдержки: `ghidra-updater/dock-updater-protocol-evidence.c`, ссылки: `dock-updater-protocol-refs.tsv`. В отдельных функциях и данных подтверждены:

- `0x725DA0` и `0x727330`: BA/C0, BA/C2, блоки64 байта и контрольная сумма;
- `0x602BC0`: OLED boot-пакет `30 55 AA 55 AA 00 00 00` изVA0x159120D;
- `0x600B00`: MLED boot-пакет `40 55 AA 55 AA 00 00 00` изVA0x1590BF5;
- `0x7288D0`: служебный опрос F7 и проверка статуса. Это не произвольное чтение flash.

Эти пакеты на физические устройства не посылались. Сам обновлятор не запускался. Наличие обработчика записи в PE не означает наличие точного OLED/MLED-образа в пакете.

### Вход в загрузчик тоже изменяет flash

Подробно разобрана функция `0x35E10`, вызываемая командой7F справочной мыши. Она обращается к flash API: стирает4096 байт по0xF000, записывает туда `AA 55 AA 55`, проверяет чтением, затем стирает4096 байт по0x6D000, вызывает инициализацию настроек и reset. Назначение всех данных этих секторов на физической1755 не установлено.

Этот путь выполнен **только в Unicorn** с синтетическими flash callbacks. Реальные инструкции функции дали указанные последовательность, адреса и длины. Flash эмулятора защищена от записи; callbacks меняют только Python-словарь в памяти. Lookup устройства, последующая инициализация и reset подменены. Доказательство: `emulated-boot-entry-side-effects.json`, воспроизведение: `python tools/emulate_reference_boot_entry.py`.

Следовательно, предложение «только войти в загрузчик и почитать» нельзя считать гарантированно пассивным. Для реального1755 соответствие кода ещё не проверено; переход в загрузчик не выполнялся.

Дополнительно изолированно выполнены обработчики USB setup `0x1624` и `0x1378`: GET_DESCRIPTOR выбирает фиксированный device descriptor0x8A5C; HID GET_REPORT — фиксированный64-байтовый RAM-буфер0x20001B6C. Изменение wIndex с0 доFFFF не превращает его в адрес памяти. GET_DESCRIPTOR с vendor request typeC0 в проверенном обработчике даёт STALL. USB register page синтетическая, физического USB нет. Пять случаев и ограничения проверки: `emulated-boot-control.json`, скрипт `tools/emulate_reference_boot_control.py`. Это проверка выбранных функций, не доказательство отсутствия иных vendor/ROM-интерфейсов.

Для проверки ответа на уже отправленный запрос AJAZZ потребовался браузер. На момент продолжения инструмент вернул `No browser is available`; пользователь получил отдельный запрос восстановить доступ к Gmail либо сообщить о наличии ответа. Новые письма и вложения не отправлялись.

Полная задача не отмечена завершённой. На физические устройства в этом продолжении не отправлялись исследовательские команды записи/стирания или перехода в boot; никакой экспериментальный образ не установлен.
