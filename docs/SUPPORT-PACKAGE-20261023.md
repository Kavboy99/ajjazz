## Полная распаковка вместо частичного потока

Ресурсы xN содержат raw DEFLATE с двумя вставками по 202 байта. Восстановление:
`temporary = raw[:1] + raw[203:]`, затем
`stream = temporary[:-203] + temporary[-1:]`.
Проверяются EOF, отсутствие хвоста, предел распаковки и хеши всех образов.
Старый исследовательский декодер, удалявший только первую вставку, оставлял
ложный хвост и не достигал EOF; его частичный результат нельзя использовать
для упаковки прошивки. Источник формата второй вставки:
[код автора YM75 patcher](https://gist.github.com/happyme531/5d1ed3225d924c2935ea1a6c417f0d22).

Воспроизведение из корня проекта:

```powershell
python tools/extract_support_firmware.py 'C:/Users/pavel/Downloads/AJ159 APEX-3950 ID：1755.rar'
python -m unittest discover -s tests -p test_support_package.py
```

Результаты: `research/vendor/ajazz-support-20261023/manifest.json` и
`{dock,mouse}/decoded/*-verified.bin`. Не прошивать `*-skip203.bin`:
это промежуточные невалидированные результаты первых опытов.

## Проверка подключённого дока

Свежие прямые Feature-чтения без службы AJAZZ:

- F1: ID1759;
- F0: USB0300 и поле chip-ID `68 05 52 30`;
- AD: OLED0104;
- повтор F1/AD успешен.

HID bcdDevice также0300. F7 не эхо-ответ с opcode F7: его поля не выдаются за
версию или RGB-конфигурацию. Сырые данные и время:
`research/local/ajazz-support-20261023/live-identity.json`.
Схема контроллеров и GPIO из этих ответов не следуют.

## Исполняемый разбор USB

USB x1 — RV32 с QingKe XW. Стандартный RV32-декодер ошибочно трактует часть
байтовых/полусловных операций как операции floating point; первоначальный
экспорт `ghidra-usb/` в этих местах неверен. Добавлен отдельный язык Ghidra,
не заменяющий стандартный RV32. Актуальный экспорт: `ghidra-usb-xw/`.
213 функций; присутствуют неразобранные инструкции и переходы, это не полный
восстановленный исходник. Экранный YC-образ: 258 функций, `ghidra-display/`;
адрес загрузки01000200 согласуется с reset thunks и абсолютными указателями.
Связь экранного кода с физическими LED ещё не установлена.

```powershell
python tools/install_ghidra_xw.py
python tools/decompile_support_usb.py
python tools/decompile_display_reference.py --family aj159-support
$env:PYTHONPATH = '.tools/py-research'
python tools/emulate_support_usb.py
```

Пять проверок оригинальных инструкций прошли в Unicorn: GET F1 возвращает1759;
GET F0 —0300 и синтетическое поле chip-ID; AD/25/28 сохраняют исходные64 байта
при подготовке пересылки. XW load/store реализованы отдельным ограниченным hook.
Это проверка GET и подготовки пакетов; USB/SPI, экран, LED, питание, радио и
реальное восстановление не эмулировались. Отчёт: `usb-emulation.json`.
Кодировки XW: [первичный разбор автора](https://gist.github.com/ArcaneNibble/461edd3bc88a5284098d48941172bfa4),
[реализация LLVM](https://github.com/llvm/llvm-project/commit/3c5f929ad093a2053b3194474609f1fc3eb15431).

## Проверка нижней кнопки

На этот раз пользователь подтвердил нажатия во время 60-секундной записи и
видимое переключение RGB. Служебная Input-коллекция FFFF/1 вернула0 отчётов.
`rgb-button-input.json` содержит подтверждение и параметры опыта.
Это подтверждает отсутствие события в этой коллекции за данный опыт, но не
отсутствие всех способов программного управления. Нельзя подменять аппаратный
драйвер RGB кнопкой в GUI или считать логическое число LED ядра количеством LED платы.

После опыта пользователь уточнил последовательность: он нажимал нижнюю кнопку,
а затем, по его воспоминанию, эффект под доком был включён с компьютера. При
последующем переборе кнопкой прежний эффект исчез. Это отдельное наблюдение;
пассивная запись FFFF/1 не позволяет ни подтвердить, ни опровергнуть последующую
отправку команды. В доступных журналах пока не восстановлены пакет, программа
и время такого включения. До воспроизведения нельзя утверждать ни что программное
управление уже найдено, ни что эффект сменился исключительно из-за кнопки.

## Незавершённая аппаратная часть

Нужно установить, к какому контроллеру и выводам подключены нижняя кнопка и LED,
тип LED/управляющей микросхемы, цепь данных и разделы хранения. Для этого полезны
фотографии обеих сторон платы дока с читаемыми маркировками и расположением
кнопки/LED; внешний вид корпуса эту информацию не даёт. При отсутствии связи
LED с программируемым контроллером одной замены экранного кода недостаточно.
Также ещё не проверены физический вход в recovery и возврат штатного экрана.

Код `firmware/dock-core` остаётся переносимым ядром, а не готовым образом платы.
AJDC не объявляется поддерживаемым штатным доком. Для установки своего BIN
требуется подтверждённый аппаратный порт. Если удастся восстановить штатную
команду управления RGB, её можно подключить к приложению независимо от этого порта.
В этом сеансе ничего не стиралось и никакая прошивка не устанавливалась.
