# AK820MAX: ревизия, подсветка и обновления

Проверено 17.10.2026. Это отчёт об исследовании, а не подтверждение готовой автономной анимации. Исполняемые пакеты производителя не запускались; прошивка, загрузчик, разделы и flash не изменялись.

## Точная цель

Подключённая клавиатура сообщает внутренние USB ID `0C45:80A0`, manufacturer `0x0166`, product `0x1004`, firmware `1.30`, frameVersion `0`, lightingVersion `0`. Через радио она доступна как `0C45:FEFC`, `AJAZZ AK820MAX`, FF80/usage 1, 32 байта данных. В USB — `AK820MAX`, FF68/usage 97, 64 байта. Дополнительный USB FF67/usage 97 имеет Output 4096 байт данных и Feature 64 байта. Наличие этого интерфейса само по себе не подтверждает поддержку анимации или конкретный MCU.

Источники: `research/local/keyboard-capabilities-rust-07.json`, `hid-caps.json`, прежние USB-снимки. Свежая дополнительная проверка `keyboard-system-query.json`: GET 0x80 ответил `55 80` с нулевым телом, без допустимой области app=0x10/boot=0x30. Версию загрузчика этим ответом установить нельзя. GET 0x10 до и после совпал. Команды 0x81–0x86 не отправлялись.

Фотографии коробки, полученные для0.12, уточняют прежнюю запись: заводской префикс именно **SGAK820MAXULTRA**, маркировка AK820MAX ULTRA / Soldier King Magnetic Axis-White, заводской EAN **6976412985287**. На наклейке импортёра указан артикул **XY-MP6-AK820MAX-ULTRA** и другой товарный EAN **7930169581016**. Общая таблица упаковки при этом говорит «AK820MAX PLUS», «400mAh» и FCC ID **2AY3H-AK820PRO**. Эти данные противоречат заводской наклейке; они не меняют подтверждённую USB-идентичность80A0. Полный индивидуальный S/N не переписывается в отчёт и не отправлялся в поиск.

По FCC ID найдено первичное заявление производителя [Model Difference Statement,7208829](https://fccid.io/2AY3H-AK820PRO/Letter/Model-Difference-Statement-7208829.pdf): AK820 MAX, AK75PRO и AK820 перечислены как варианты семейства AK820PRO. ULTRA в этом списке отсутствует. [Internal Photos,7208813](https://fccid.io/2AY3H-AK820PRO/Internal-Photos/Internal-Photos-7208813.pdf) относятся к той заявке2024 года; их наличие не доказывает модель контроллера конкретной магнитной ULTRA. Сырой HTTP-доступ к PDF из локального загрузчика вернул403; маркировка микросхем по этим фото не установлена. Никакие пакеты PRO/PLUS из-за совпадения FCC ID не выбирались для прошивки.

## Как сайт различает модели

В сравнении 0.10 на подключённом 2.4G сайт установил mode1/#ff0000/mono. Пользователь подтвердил красный на физических клавишах, а GET13 сохранил default white/RGB. Поэтому полное сравнение цвета с GET ошибочно откатывало рабочий SET23. Rust теперь принимает только этот точный известный fallback для native0–19, проверяя все остальные поля, и отдельно отмечает, что цвет не проверяется чтением. Встроенный режим изменяется коротким SET23, без чтения/перезаписи RGB512: 1,315→0,278 с. Полная таблица 0x24 остаётся отдельной операцией.

Новый кандидат `https://www.ajazzdriver.com/files/20260923-194542-bfb55d6c-AK820MAX-Ultra-Upgrade.rar` пока не получен. HTTP вернул HTML «One moment, please…»11960 байт; файл, скачанный пользователем в Edge, — локализованный HTML «Секундочку…»11991 байт, начало `<!DOCTYPE html>`, SHA256 `fcd600aae8deb41d5c34ddaa5502df73edea7a1ae5435e866e8fa2bf791a478c`. Он не является прошивкой или RAR, запуск/прошивка не выполнялись. Пакеты illumipc содержат другие AK820MAX на VID0416:7372, не текущий80A0.

Извлечены 33 конфигурации из трёх снимков: май, июнь и октябрь 2026. Октябрьский архив содержит побайтно тот же `layout-classic-0DHAQysC.js`, который получен с [веб-драйвера AJAZZ](https://ajazz.driveall.cn/). Исторические снимки: [ajazz-driver-artifact](https://github.com/xyzmean/ajazz-driver-artifact/releases).

Во всех трёх снимках точный 80A0 имеет 82 клавиши, маршруты customKeys, lighting, macro, performance, advancedKeys, settings и RS/SOCD/DKS/MT/TGL. У него нет `musicConfig`, `lightingConfig.isShowGifEffect`, маршрутов `led`/`tft` и флага отображения Fn-редактора. Общая библиотека содержит дополнительные функции для других устройств; они не становятся возможностями 80A0 автоматически.

SignalRGB также не даёт готового пути для нашей ревизии. [Nuvoton-плагин](https://gitlab.com/signalrgb/signal-plugins/-/blob/Development/Plugins/Nuvoton/Nuvoton_Keyboard_Controller.js) имеет VID 0416. У нас другая пара PID/интерфейс; команды этих плагинов не отправлялись.

## Что передаётся для подсветки

| Путь | Формат | Что установлено для 80A0 1.30 |
|---|---|---|
| Штатный автономный эффект | 0x23, 16 байт: mode, RGB, FF, secondary RGB, colorMode, brightness, speed, direction, effectModeType, 00, AA55 | Работает. Анимацию вычисляет клавиатура |
| Один пользовательский кадр | 0x24, 128×[ID,R,G,B], стандартный адресный заголовок | Работает. Многократное обновление видно сверху вниз; тип памяти не установлен |
| Временный USB RGB | 0x32, [ID,R,G,B], effectIndex в byte 5, промежуточный flag 0, последний 1 | Ответы были, видимого изменения в предыдущих физических тестах не было |
| Радио RGB | 0x35, короткий AA/35/chunk/effectIndex, RGB565; отдельный формат 0x3C для lightingVersion=1 и 64 байт | 0x35 не дал видимого изменения. Вариант 0x3C не соответствует объявленной версии нашего устройства |
| Автономная RGB-анимация | **0x42**, отдельный поток с числом кадров и задержкой, без ID в RGB-массиве | Реализован в общей библиотеке сайта, поддержка 80A0 не подтверждена |
| Dot matrix / TFT | 0x41/0x42 и 0x50/0x51, другие форматы и назначения | Не путать с RGB клавиш или дисплеем мышиного дока |

У автономного GIF-пути две части:

1. UI выбирает режим 255 через 0x23. Заголовок данных — `frameCount LE16`, `ceil(106-speed) LE16`; после него для каждого кадра идут RGB-тройки клавиш в порядке `keyList.flat()`, исключая disabledLight. ID клавиш отсутствуют. В браузерном предпросмотре значение `106-speed` умножается на 20 мс; единица времени аппаратного проигрывателя на нашей прошивке не проверена.
2. OZ/setGifLighting для USB выбирает авторизованный интерфейс с тем же PID и usagePage FF67. Данные режутся по `reportCount-8`. Заголовок пакета: `AA 42 indexBE16 totalBE16 00 00`; остальное — данные и нулевое заполнение. На наблюдённом USB-дескрипторе это 4088 байт полезных данных на report.

В коде total считается выражением `floor(dataLength/capacity)+1`, тогда как число реально посылаемых пакетов равно `ceil(dataLength/capacity)`. При точном кратном это расходится; переносить это выражение без проверки обработчика firmware нельзя. Сохранена точная аналитическая реализация сайта и тест этого случая. На устройство эти пакеты не отправлялись.

GET 0x10 читает tftMaxFrames из payload 22–23, gifMaxFrames из 24–25, ledMaxFrames из 26–27. Наши RF/USB-снимки дают 0/0/0. Сайт ограничивает загрузку числом gifMaxFrames: простое включение скрытой вкладки при нуле не загрузит желаемые кадры. Это не доказательство физического отсутствия памяти; нужен обработчик именно нашей firmware.

0x30/0x31, 0x34, 0x40 и 0x4F объявлены как константы, но рабочего вызова в исследованном bundle не найдено. У 0x4F нет доказанного пути чтения flash; использовать название команды как разрешение на дамп нельзя.

## Обновления: два разных механизма

И старые снимки, и текущая версия получают `https://ajazz.driveall.cn/update.json`. HTTP helper не добавляет скрытый API-префикс. Повтор с заголовками сайта вернул HTTP 200, application/json, **0 байт**. Единственная найденная запись Wayback для этого URL (22.09.2025) имеет SHA-1 пустого тела. Это не полноценный архив прошлых прошивок и не доказательство, что каталог всегда был пустым.

Запись обновления выбирается по `entry.productId === GET_INFO.pid` и точному `entry.productName === HID.productName`. Для радио нельзя подставить FEFC вместо внутреннего 80A0; имя сравнивается с именем HID текущего канала. Далее возможны:

- `isHex`: загрузка файла, выбор MCU и параметров безопасности, разбор HEX в `sn_isp_lib_bg-DOswDDJh.wasm`, затем Feature ISP. Это отдельный протокол. Сайт выбирает любой интерфейс того же PID с Feature reports; MCU из GET 0x10 не определяется.
- Новая OTA-ветка: 0x81 проверяет manufacturer/product; при необходимости 0x82 переводит в boot; 0x80 проверяет область; 0x83 передаёт образ. Пакеты не пересекают границу 4096 байт. Заголовок `AA 83 packetBE16 countBE16 lengthU8 crcBE16`; CRC-16/CCITT-FALSE (poly1021, initFFFF) передаётся на границе блока и в конце. Промежуточное поле CRC=FFFF. Это **не** подтверждённый путь обновления нашей frameVersion=0.

WASM скачан (80442 байта, SHA256 `8816f7c9a112265943f0137d1d54b4c9fc13d87850803918d5e53a9569aacba6`), преобразован в WAT. Экспорт `set_chip_series_index`, function 114, принимает только 0–3:

| WASM index | Встроенное имя |
|---|---|
| 0 | SN34F280 |
| 1 | SN32F24xB |
| 2 | SN32F268 |
| 3 | SN32F290 |

В JS перечислены типы 1/2/3/4/5/255 и вызывается `set_chip_series_index(type == 255 ? 1 : type)`. Для 4 и 5 WASM возвращает false, результат игнорируется; JS-имя типа 2 также не соответствует имени WASM index 2. Проверено в изолированном Wasmtime: **все host imports заменены функциями, которые бросают исключение**; выполнен только локальный selector, HID/сеть/файлы ему не предоставлялись. Это найденное несоответствие конкретного набора JS/WASM, не установленная причина какого-либо сбоя клавиатуры.

## Продолжение разбора встроенных алгоритмов

На подключённом сайте подтверждена ошибка проверки обновлений: UI сообщает «Уже последняя версия», но тот же запрос падает при разборе пустого JSON. Для близкого образа статически найдены SET23, таблицы инициализации/шага и RGB-буферы; восстановленный шаг волны совпал с исходными ARM-байтами в192 шагах эмулятора. Блок самого образа подтверждает8033/1.04/product0000, а не80A0/1.30/product1004. Подробности, адреса, границы выводов и воспроизведение — [FIRMWARE-LIGHTING-RE.md](FIRMWARE-LIGHTING-RE.md). Совместимый патч не создан.

## Чего именно не хватает

Для требуемой загрузки собственной анимации в память нужны: точный образ `80A0 / manufacturer0166 / product1004 / 1.30` либо доказанно совместимое обновление; идентификация MCU и платы; разбор dispatcher 0x23/24/32/42 и карты flash; формат области кадров и механизм переключения кадров; способ резервирования/восстановления radio-параметров и Hall-калибровки. Пока не установлено, есть ли готовый обработчик 0x42, можно ли включить его параметром или потребуется менять firmware.

Состояние программных функций в0.12: макросы, основной цвет/RGB-палитра встроенных эффектов, сочетания и функции мыши перенесены. Быстрый видимый красный пользователь подтвердил в0.10. Редактор второго цвета не включён; требуется завершить физическую проверку RT, макросов и переназначений. В 0.8 добавлены MT/TGL и парные RS/SOCD; семь USB-циклов записи, чтения и возврата прошли. В 0.9 добавлен DKS с проверкой и возвратом двух блоков, его USB-цикл также прошёл. Физическое поведение этих назначений ещё не проверено. Fn/TFT/музыкальный режим из общих модулей нельзя объявлять пропущенными возможностями нашего точного профиля без дополнительного подтверждения. Полная матрица приложения — FEATURES.md.

Повторное сравнение с подключённым сайтом выявило ошибку нашего transport: custom записывается как 128, возвращается как 20. В 0.8 это преобразование вынесено в кодек команды SET; пользовательский режим включается до загрузки таблицы. USB-цикл кадра и полный возврат прошли. Отдельный тест mode1/red/colorMode0 снова прочитал FF/FF/FF/colorMode1, после чего исходные шесть блоков восстановлены; в0.8 редактирование встроенных цветов ещё не было включено. В0.10 сравнение с сайтом выявило точный white/RGB fallback чтения; после исправления короткого пути пользователь подтвердил быстрый красный в GUI. Это не изменило ограничений пользовательских анимаций.

Для RGB дока и собственных автономных часов остаётся другой отдельный пробел: нужен образ именно dock ID1759/OLEDV104 и его обработчик RGB/таймера. Успешная загрузка GIF экрана не подтверждает API светодиодов дока и не раскрывает его firmware. Прошивка клавиатуры этот вопрос не решает.

Повторно разобрана маршрутизация обновлений установленного AJAZZ Driver(R)2.1.94 и qmk.top: оба используют api2.rongyuan.tech:3816/api/v2/get_fw_version, поле dev_id. Для ID1759 ранее получен Record not found; дополнительный запрос mouse ID1755 также вернул HTTP500/Record not found. Это ответ каталога, а не доказательство отсутствия обновлений у производителя. В распакованной установленной программе и её каталогах Roaming/Local отдельного firmware BIN/HEX/ZIP не найдено; v8_context_snapshot.bin и snapshot_blob.bin принадлежат Electron.

## Воспроизведение

`tools/audit_keyboard_revision.py` читает только локальные файлы, извлекает конфигурации без выполнения JS, проверяет HEX и строит аналитические пакеты GIF/OTA без HID. Результат: `research/local/keyboard-revision-audit.json`, 33 профиля и хеши полученных файлов. `tools/probe_keyboard_system_info.py` отдельно ограничен GET 0x10/0x80 и использует общий mutex приложения. `tools/extract_qt_resources.py` извлекает Qt v1 ресурсы из PE по статически установленным адресам трёх таблиц, не загружая исполняемый код. Сырые vendor-файлы игнорируются Git; они не являются инструкциями для выполнения.
