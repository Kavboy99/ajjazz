# Исследование AJAZZ

## Уточнение 0.6: воспроизведение и прямой RF

Повторно скачанный 17.10.2026 основной JS веб-драйвера совпал по SHA-256 с исследованным: 7edaa333a9272feebc8406c33ea07f43cb8051c8b30f7eda8693e9071142638d. Предыдущее приложение Lighting Lab из соседнего проекта использовало 0x23 (mode 128) и последовательные 0x24, а не 0x32/0x35. На USB firmware нормализовала mode 128 в 20, восемь таблиц считались обратно точно; пользователь подтвердил реальное чередование. Подробнее — ANIMATION.md. Невозможность анимации из неудачи 0x32 выводить было ошибкой.

Мышь теперь использует собственный HID: F1=1759, маршрут F6/05, статус F7, ответ через FC, ID 8F=1755. D3/D4/D0 и записи 53/54/09 проверены полным циклом с закрытой службой производителя; все исходные байты восстановились. Конкурирующий процесс ранее вызвал несовпадение команды ответа; перед открытием добавлена проверка его локального порта.

У точного дока common_dangle метод upgrade в установленном клиенте возвращает false. Универсальная кнопка обновления и код загрузчика других моделей не доказывают совместимость с ID1759. Точный MCU-образ ещё не получен, команды boot/erase/firmware write не выполнялись.


## Изменения реализации 0.3

Временный мост теперь допускает строго D3/D4 GET и 53/54 SET для AJ159 APEX ID1755. Перед записью сравниваются свежие исходные данные и профиль, сохраняется синхронизированная на диск копия. После — чтение и сравнение; при ошибке восстанавливаются все затронутые блоки, включая тот, отправка которого могла завершиться без подтверждения. Checksum byte 7 исключён из сравнения параметров. Другие байты сохраняются. У конфигурации `_l`: banXY=true, восемь ступеней, диапазон 50–42000 с шагом 50, debounce минимум 2 и UI максимум 10, LOD низкий/средний/высокий (коды 0/1/2, без неподтверждённых миллиметров).

Включение Rapid Trigger определяется ненулевыми pressRT/releaseRT; flags bit0 — isWholeFast, bit1 — isRampageMode. Это отдельные параметры. Нулевые axis/actuation используются штатным UI как значения по умолчанию; при чтении на WASD actuation=0.10, остальные видимые клавиши — default 1.20. Запись меняет только выбранные matrix IDs, сохраняет неизвестные bits. GET 17/SET 27 проверены циклом F12. До и после сравниваются все шесть конфигурационных блоков. Восстановление не записывает значения в другой профиль.

Переназначения 0x12/0x22: 128×4 байта. Default=[0,0,0,0], Keyboard=[2,0,usage,0], Consumer=[3,usageLE16,0]. Проверен F12→F11→default. Fn имеет physical=-1/HID0 и не переназначается; записи с непренесёнными advanced pages остаются неизменными. LED 0x13/0x23: byte0 mode, 1..3 RGB, 4 driver marker FF, 5..7 secondary RGB, 8 color mode, 9 brightness, 10 speed, 11 direction, 12 effectModeType, 14..15 AA55. На 1.30 GET нормализует RGB/colorMode в FF/FF/FF/1 даже после SET другого цвета. Эти поля не считаются рабочими. Сохранены отдельные ошибки проверки и исходная подсветка восстановлена. Mode7/brightness4/speed3 принят без изменения RGB-матрицы.

Описания read-only и отсутствия записи ниже отражают предыдущую стадию 0.2. Текущее состояние функций — в FEATURES.md и VALIDATION.md.

## Установленная система

ОС Windows. AK820MAX подключена через свой 2.4 GHz донгл, AJ159 APEX — через док. Пользователь подтвердил, что веб-драйвер умеет менять настройки клавиатуры через этот донгл.

| Устройство/интерфейс | VID:PID | Usage page / usage | HID размеры с байтом report ID |
|---|---|---|---|
| AK820MAX, MI_02 | 0C45:FEFC | FF80 / 0001 | input 33, output 33 |
| AK820MAX, MI_03 | 0C45:FEFC | FF70 / 0071 | input 65, output 65 |
| APEX dock, MI_02 | 3151:5007 | FFFF / 0002 | feature 65, input/output 0 |

Модель клавиатуры подтверждена USB product string `AJAZZ AK820MAX`. Остальные интерфейсы системного ввода перечисляются, но не открываются для конфигурационных запросов. Идентификатор 3151:5007 используется и другими устройствами OEM; одного VID/PID недостаточно для выбора протокола конкретной мыши.

Установлен AJAZZ Driver（R） 2.1.94. Его окно для дока показывает `ID1759_OLEDV104`. В пакете есть и более новая конфигурация `dangle_3950b` ID2350; она не должна автоматически выбираться для данного дока. Для ID1759 используется `common_dangle`.

Программа: `%LOCALAPPDATA%/Programs/AJAZZ Driver（R）/resources/app`. Renderer — `dist/static/js/main_ace02afb.js`, main process — `main_dist/main.js`. Служба сейчас выполняется из `%APPDATA%/AJAZZ Driver（R）/iot_driver_v193.exe`. Строки executable подтверждают Rust, tonic/tonic-web и HID SDK. Это программная служба Windows, не firmware MCU.

## Современный протокол клавиатуры из веб-драйвера

Пакет output имеет 32 или 64 **байта данных** плюс report ID `0` для hidapi. Для подключённого FF80 проверен размер 32.

```
0      AA             host header
1      command
2      payload length
3..4   address LE16
5      optional header
6      final packet flag, unless overridden
7      reserved/optional header
8..    payload
```

Ответ начинается с `55`, содержит command/address и данные с offset 8. Драйвер дробит блок на части по `report_size - 8`. Для GET_DEVICE_INFO: длина 48, два запроса по 24 байта, адреса 0 и 24. Соответствующие заголовки:

```
AA 10 18 00 00 00 00 00
AA 10 18 18 00 00 01 00
```

Перенесённый код проверяет команду, адрес и длину ответа; завершает чтение по тайм-ауту. Первые запросы не отвечали, аналогичные ошибки были в журнале сайта. После подключения пользователем на сайте ответы получены и в независимом Python probe, и в Rust CLI. Причина первоначального отсутствия ответов не установлена; нельзя утверждать, что сайт обязательно нужен для каждого запуска.

Фактический `GET_DEVICE_INFO`: версия 1.30, внутренние VID/PID 0C45:80A0, manufacturer 358, product 4100, work mode 2, батарея 32%, профиль 0, RT/frame/lighting precision/version 0, firmware status 0. Это объясняет отличие внутреннего PID от USB PID приёмника FEFC.

Прочитаны device info, game mode (56), keymap (512), lighting (16), custom RGB (512), RT (1024), DKS (1024). Это конфигурационные блоки, а не firmware backup. Фактический режим пользовательской подсветки у 1.30 — **20**. В новом общем модуле сайта CUSTOM_LIGHTING_MODE=128; UI отдельно распознаёт 20/21/128. Для этой ревизии сохранён проверенный mode 20.

`tools/lighting_roundtrip.ps1` выполнил цикл на устройстве: записал кадр сцены, прочитал полный снимок, восстановил предыдущую RGB-матрицу и режим, снова прочитал. `research/local/lighting-roundtrip.json`: rgb_changed=true, rgb_restored=true, lighting_restored=true, other_blocks_unchanged=true. Поля 4/14/15 LED-блока служебные: штатная запись устанавливает FF/AA/55, а проверка сравнивает остальные параметры. Неиспользуемые matrix slots сохраняются из исходного блока. Внешний вид LED не наблюдался.

После программной проверки пользователь подтвердил видимую смену цветов при нажатии «Применить кадр» и успешное чтение мыши из GUI 0.2. Данное подтверждение относится к физическим устройствам пользователя; поле physical_led_appearance_observed=false в автоматическом JSON-тесте отражает отсутствие машинного визуального наблюдения в самом скрипте.

В приложении разрешены только записи 0x24/0x23 для точной подтверждённой identity/версии. До записи создаётся синхронизированная на диск JSON-копия и повторно сверяются профиль/исходные данные. После записи проверяется чтение; при ошибке выполняется попытка возврата, если профиль не изменился. Ошибку восстановления приложение показывает явно.

Дополнительный source-confirmed запрос живых RGB 0x37 вернул 82 нулевых цвета и battery=0. Это не подтверждает рабочую обратную связь текущих LED на данной ревизии. Direct mode в GUI не включён.

Проведены ограниченные тесты временных кадров: 0x35 (radio RGB565, 82 цвета по порядку строк) и 0x32 (RGB24 с matrix ID, 8-байтный заголовок, переданный через тот же радиоинтерфейс). Пользователь сообщил, что в обоих тестах остался статический кадр. Первое короткое «да» было затем отозвано пользователем: он не успел увидеть результат; оно не считается подтверждением. Для 0x32 получены ACK `55 32 len addr...` с эхом данных, но это **не доказательство вывода цветов**. Тесты сохраняют исходную подсветку и возвращают её через проверенный путь после завершения.

В qG для AK820MAX отсутствует musicConfig, хотя общий веб-бандл содержит setMusicData для других конфигураций. Это может объяснять неприменимость общего direct mode, но не устанавливает аппаратного ограничения. Необходимы доказательства режима включения/другого транспорта или анализ точной firmware. Записывать статическую матрицу 0x24 на каждом кадре вместо direct mode нельзя.

После физического выключения/включения клавиатуры повторный Rust snapshot прошёл: все шесть блоков (custom RGB, lighting, keymap, game mode, RT, DKS) совпали с состоянием перед перезапуском. Пользовательское сохранение подсветки пережило эту проверку. Дополнительный тест 0x32 после перезапуска завершился возвратом исходного состояния; пользователь снова не наблюдал чередования и подтвердил, что «Применить кадр» в нашем GUI по-прежнему работает. Точное время этого ручного применения относительно теста неизвестно: конкурентную запись следует исключить в следующем контролируемом опыте. Сам GUI не посылает фоновые RGB-пакеты. Причина отсутствия вывода временных кадров ещё не установлена, утверждение «firmware вообще не поддерживает direct mode» не доказано.

Полезные данные:

- Device info 48 байт: VID/PID, BCD version, manufacturer/product, work mode, battery, charging, profile, RT precision, frame version, lighting version, firmware status.
- Game mode 56 байт: время сна, задержка, системный режим, мёртвые зоны, стабилизация, автокалибровка, NKRO, частота радио и питание.
- Custom RGB 512 байт: 128 записей `[matrix_id, R, G, B]`.
- RT 1024 байта: на клавишу axis, flags, actuation LE16, press RT LE16, release RT LE16. Для precision 0 делитель 100; precision 1: RT /1000, actuation /100; precision 2: всё /1000. Неизвестные bits flags при patch сохраняются.
- Макросы: таблица 100×LE32 указателей, затем заголовки и события. Общая длина и flash geometry требуют отдельной проверки.
- Стриминг имеет разные форматы USB/2.4G, в том числе RGB565 и версии команд 0x35/0x3C. Нельзя использовать запись статических цветов во flash на каждом кадре.

## Мышь и служба

Renderer общается с `127.0.0.1:3814`, gRPC-web service `driver.DriverGrpc`. Найдены RPC `sendMsg`, `readMsg`, `sendRawFeature`, `readRawFeature`, `watchDevList`, `watchVender`. Native-служба добавляет checksum и выполняет маршрутизацию. Полная реконструкция этого слоя пока не выполнена.

`local_bridge.rs` реализует `watchDevList` и строго ограниченные GET D3/D4 через `sendMsg/readMsg`, BIT7=0, DangleDevType.MOUSE=2. Он ограничен loopback, тайм-аутом и размером сообщения. Произвольных RPC/HID-команд в публичном API нет. Батарея, ID и флаг online декодируются отдельно. Мост пока зависит от штатной службы и не заменяет независимый HID-драйвер.

Фактический mouse ID 2147485403 = 0x800006DB, профиль семейства ID1755 AJ159 APEX. Сначала `isOnline=false` и `dev is not online`. После физического действия пользователя и перехода на мышь появился online=true; GET D3/D4 вернули корректные блоки. Оба состояния наблюдались, причина перехода отдельно не установлена. D3: profile 0, polling 0x81=8000 Hz, debounce 2 ms, X/Y sensitivity 100, LOD code 1, angle snap 0. D4: current index 2 (1200 DPI X/Y), count 8, X/Y `[400,800,1200,1600,2400,3200,42000,0]`. Необычные 42000/0 сохраняются как полученные значения; они не доказывают максимальный диапазон устройства. У выбранного профиля производителя `banXY=true`, поэтому наличие двух массивов в протоколе не доказывает поддержку независимой настройки X/Y.

Первая попытка GET OLED version AD через sendMsg/readMsg вернула нулевой блок без корректной команды. В точном классе qpa обнаружен другой путь: commomRawFeature с 64-байтным AD и BIT7, route NONE. Он вернул `AD 04 01 00 00...`: raw OLED version 0x0104, raw flashVersion=0. Это соответствует штатной надписи OLEDV104, но не определяет flash geometry.

Отдельный `tools/probe_dock_version.py` повторил GET AD напрямую через HID Feature, без RPC службы: report ID 0, 64 байта данных, checksum в data[7] = FF − sum(data[0..7]). Для GET AD checksum=52 hex. Ответ 65 байт `00 AD 04 01 00 00...` подтверждён на доке. Эта исследовательская команда пока не добавлена в GUI 0.2.

Пассивный feature-read после D3: HID report начинается с `00 00 00 50 01 00 01 02`, затем данные option0. Для мыши служба использует собственную обёртку: работа прямого AD к доку не доказывает возможность посылать логический D3 напрямую к мыши.

Mouse option0: read 0xD3 / write 0x53, 64 байта. Profile offset 8, polling code 9, debounce 10; flags 12..13; sensitivity X/Y 50/51; lift cut-off 52; angle snapping 53. Patch должен начинаться с исходного блока и сохранять остальные поля. Таблица кодов частот ещё не перенесена.

DPI — 0xD4/0x54, кнопки — 0xD0/0x50, Fn — 0xD1/0x51. Передача мыши через док использует отдельную маршрутизацию; команды dock screen и mouse settings смешивать нельзя.

## Экран и прошивка дока

Конфигурация `common_dangle` ID1759: RGB16, 128×128, пять слотов. Класс `qpa` обслуживает экран: OLED version 0xAD, GIF data 0x24, TFT data 0x25, метаданные 0xA5, clock 0x28. Встречается операция erase 0xAC. Она **не включена** в наше приложение.

Код интерфейса выполняет упаковку изображения, разбивку по 56 байт, установку метаданных и ожидание подтверждений. Показанное в редакторе RGB565 BE — только стандартный экспортный формат, не доказанный формат загрузки в док. Компрессию и порядок байтов нужно проверить отдельно.

Наличие радуги дока не доказывает host-команду на каждый LED. Эффект может полностью исполняться MCU, а нижняя кнопка только выбирать встроенный режим. Аналогично штатный updater может проверять подпись, шифрование или ревизию; возможность загрузить модифицированный образ пока неизвестна.

В установленном пакете, архиве и доступном файловом кэше образ MCU не найден. Штатный endpoint `https://api2.rongyuan.tech:3816/api/v2/get_fw_version` с публичным `dev_id=1759` вернул `Record not found`. Перебор чужих ревизий и установка обновлений не выполнялись.

Контроллер, архитектура, разметка flash, формат образа, контрольные суммы/подписи и аппаратный recovery не определены. Обозначение PAN1080 в имени семейства драйвера само по себе не является идентификацией MCU дока.
