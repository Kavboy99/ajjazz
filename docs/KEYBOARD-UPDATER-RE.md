# Разбор прошивальщика AK820MAX и расширение поддержки ревизий

Проверено 26 октября 2026. Исследование исходного EXE от поддержки, второго
пакета AK820MAX и уже сохранённых материалов проекта. Исходный обновлятор
не запускался процессом Windows; клавиатура в этом исследовании не
перезагружалась и не перепрошивалась. Семь функций исходного x86-кода
исполнялись изолированно в Unicorn с заменёнными USB-вызовами.

**Вывод: собственный обновлятор внутри Studio технически реален.** Производитель
использует общий SONiX ISP Tool с заменяемыми ресурсами. Его движок не привязан
только к AK820MAX ULTRA. Уже получены самостоятельный извлекатель пакетов,
восстановленный кодек и проверяемый каталог ревизий. Это исследовательское
ядро: аппаратная реализация собственной записи ещё не испытана и в интерфейс
Studio не подключена. Наличие нового профиля в каталоге не объявляется
поддержкой записи на физическую клавиатуру.

## 2. Контейнер и фактически выбранная прошивка

EXE — нативный PE32 x86, база `0x00400000`, MFC/Visual C++. Зависимости включают
HID.DLL, SETUPAPI и стандартные библиотеки Windows. Для получения образа не
нужно загружать EXE или DLL: достаточно разобрать дерево ресурсов PE.

| RCDATA | Содержимое в пакете 1.36 | Значение |
|---|---|---|
| 4000 | 516 096 байт | Активный пользовательский образ |
| 4007 | UTF-16LE `12345678` | Значение поля ISP-пароля; само по себе не доказывает применение в каждой ветке |
| 4008 | `0C45` | VID приложения |
| 4009 | `80A0` | PID приложения |
| 4010 | `SN34F280` | Выбор семейства MCU |
| 4011 | ZIP, 126 957 байт | UISettings, изображения, шаблонный HEX |
| 4012 | 1 байт | Настройка CodeSecurity, читаемая загрузчиком ресурсов |
| 4013 | `Build time:2025/06/30 09:24` | Метаданные сборки |
| 4014 | `67E7` | Сумма 16-битных little-endian слов образа, modulo 65536 |
| 4016 | `SN34F280_User.hex` | Имя прошивки в UI |

Доказательство выбора образа: `FUN_00427120`, в том числе инструкция по
`0x00427276`, вызывает FindResourceW для **4000**, затем
LoadResource → LockResource → SizeofResource → memcpy в рабочий буфер.
Это сильнее предположения по расширению файла или его имени.

`FUN_00426250` отдельно распаковывает ZIP из ID4011 (`0xFAB`).
Он записывает `SettingFiles.zip` во временный каталог и извлекает настройки.
Этот путь не меняет установленный факт первоначальной загрузки RCDATA4000.
В новой утилите весь разбор ZIP остаётся в памяти; исполняемый код и скрипты
архива не запускаются.

### Почему нельзя брать первый найденный HEX

В пакете 1.36 вложенный HEX имеет другую идентичность: `0C45:80BE`, версия
`0x0117`. Его 92 172 явно заданных байта имеют корректные Intel HEX checksum,
но **77 665** из них отличаются от активного образа 1.36. Следовательно,
проверка синтаксиса HEX не делает его правильной прошивкой для80A0.

У recovery-пакета активный RCDATA4000 сообщает PID8033 / `0x0104`, поле
RCDATA4009 содержит `7903`, а UISettings включает8033/8070. Его вложенный HEX
тоже не совпадает с активным образом: 58 313 отличающихся заданных байтов.
Эти уровни необходимо хранить раздельно: метаданные приложения, список UI,
образ, загрузчик. Одно значение не заменяет остальные.

В 1.36 `[SpecialPID] Count=0`: существующие в INI секции SpecialPID0..3
не активируются просто из-за своего присутствия. `FUN_00423F80` сначала
читает Count и обходит только указанное число записей. У старого пакета
Count=2, поэтому его8033/8070 действительно входят в этот список.
`FUN_00423000` поддерживает ещё одну таблицу — ProgramByDeviceVersionInfo;
в данном INI она не задана. Новая реализация должна различать такие ветви,
а не объединять все встретившиеся PID в разрешающий список.

## 3. Обновлятор действительно общий

Сравнение двух EXE выполнено побайтно, отдельно от ресурсов:

| PE-секция | Размер raw | Результат |
|---|---:|---|
| `.text` | 1 416 192 | Полностью одинаковая |
| `.rdata` | 318 464 | Полностью одинаковая |
| `.data`, сохранённые в файле байты | 43 008 | Полностью одинаковая |

Хеш `.text`: `711ec8d76d81b39758372a8154663317475dccb3644cda950a9a5683c3017260`.
Таким образом, для этих двух пакетов это один код обновления с разными
ресурсами. Это прямое доказательство повторного использования движка,
но не совместимости двух firmware-образов.

Из таблицы по `0x005B30A8`, шаг51 байт, восстановлены22 записи семейств.
В них есть SN8F, SN32F229/239/249, SN32F268, SN32F248B, SN32F280,
SN32F290, SN32F24xC и **отдельный SN34F280**. Полные записи и дескрипторы
сохранены в `chip-table.json`; наличие записи не означает, что её ветка
проверена на устройстве.

Для важных соседних записей:

| MCU | Boot VID:PID из таблицы | Сигнатура version | Erase count | Блоки64 |
|---|---|---|---:|---:|
| SN32F280 | `0C45:7120` | `20 04 00 00` | 128 | 2048 |
| SN32F290 | `0C45:7140` | `20 05 00 00` | 256 | 4096 |
| SN32F24xC | `0C45:7160` | `20 06 00 00` | 128 | 2048 |
| **SN34F280** | **`0C45:7210`** | **`20 08 00 00`** | **504** | **8064** |

Это ожидаемые ID из EXE, не результат переключения подключённой клавиатуры
в boot mode в этом сеансе. Именно поэтому нельзя подставить профиль SN32F280
из стороннего flasher: у него другая геометрия. В открытом
[SonixFlasherC](https://github.com/SonixQMK/SonixFlasherC/blob/main/src/chip.c)
исследованный список содержит SN32F280 и не содержит отдельной записи
SN34F280. Использовать проект как справочник протокола можно, переносить
его таблицу вместо OEM-таблицы — нельзя.

## 4. USB-путь и пакеты

Обычное управление клавиатурой и ISP — разные протоколы. Настройки приложения
используют AA/55 и свои команды. Наличие ответа на обычную команду0x80
не удостоверяет готовность к ISP. Команды0x81–0x86 из другой OTA-ветки
веб-драйвера не заменяют восстановленный здесь ISP.

`FUN_00428F20` перечисляет HID через SetupDi, читает атрибуты и HID capabilities,
отбирает VID/PID, размер Feature и report ID0; опционально сравнивает имя
устройства. `FUN_00428930(n)` задаёт ожидаемую длину Feature как `n+1`.
Выбор длины зависит от ветки; начальное значение глобальной переменной —9.
В рассматриваемой ветке данных размер payload64, Windows Feature report65.
Не следует переносить размер4096 из другого HID-интерфейса клавиатуры.

`FUN_00428680` выполняет SET_FEATURE, `FUN_00428810` — GET_FEATURE. Они
добавляют/снимают первый байт report ID0, открывают путь через CreateFileW
и закрывают handle после операции. При невозможности открытия read/write
есть повтор с desiredAccess0. Перед копированием длина ограничивается
`FeatureReportByteLength - 1`.

**Все смещения далее относятся к payload без report ID.** Нельзя добавлять
или убирать этот байт дважды при переносе в hidapi.

| Действие | Начало payload | Поля / исходная функция |
|---|---|---|
| Вход в ISP | `AA 55 A5 5A FF 00 33 CC` | Из CheckDeviceCmd; `0x0040D4C0` |
| Версия загрузчика | `01 AA 55 00` | 64 байта; `0x0040B6A0` |
| Compare / подготовка CodeOption | `02 AA 55 00` | Bulk-ветка `0x0040BAC0`; далее нули в моделируемом CS0-контексте |
| CodeOption / security | `03 AA 55 00` | optionLE16 @4, securityLE16 @6; `0x0040B9D0` |
| Стирание | `04 AA 55 00` | startLE16 @4, endLE16 @8; `0x0040BB20` |
| Подготовка записи | `05 AA 55 00` | offset0 @4..7, число блоковLE16 @8; `0x0040BDF0` |
| Данные | Сырые64 байта образа | Без добавленного AA-заголовка и номера пакета |
| Get checksum, отдельный helper | `06 AA 55 00` | 8 байт; `0x0040BEA0` |
| Выход в приложение | `07 AA 55 00` | 8 байт; `0x0040C140` |

Конкретные первые12 байт команд для SN34F280:

```text
erase:   04 AA 55 00 00 00 00 00 F8 01 00 00
program: 05 AA 55 00 00 00 00 00 80 1F 00 00
```

`0x01F8 = 504`, `0x1F80 = 8064`, `8064 × 64 = 516096`.
Это согласуется с размером RCDATA4000. В документации производителя
[SN34F280 Quick Start](https://www.sonix.com.tw/download/file?b05d94e5496d4be79ad82d8fbf6498e3=)
также встречается504KB User ROM. Полный PDF этим веб-инструментом не получен;
геометрия выше установлена независимо по EXE и объёму передаваемых данных.

### Последовательность и проверки

`FUN_00407530` переводит устройство в нужный режим, получает version и сверяет
четыре байта с выбранной записью таблицы. `FUN_00407CA0` ведёт основную запись:

1. Подготовить option/security для выбранного MCU. Для SN34F280/CS0 код
   использует нулевое значение; существуют отдельные запреты и ветви для
   других уровней security. Снятие защиты не считается универсальным шагом.
2. Выполнить подготовительные команды и стирание.
3. Прочитать blank checksum по смещению8; ожидаемое значение для SN34F280 —0.
4. Отправить command5 и потребовать совпадение первых4 байт ответа и
   `FA FA FA FA` по смещениям4..7.
5. Последовательно передать8064 сырых блока64.
6. Выполнить GET_FEATURE и сравнить16-битную сумму по смещению8 с суммой образа.
7. При выбранном соответствующем поведении отправить возврат в приложение.

Основной путь после данных читает результат через GET_FEATURE; он не обязан
посылать command6. У отдельного helper command6 другой компактный разбор
ответа. Смешивать эти два формата нельзя.

Часть подготовительных операций в OEM подтверждается только успешным
SET_FEATURE. У проверки blank/final checksum нет такой же строгой проверки
заголовка/ACK, как у command5. Это описание оригинала, не рекомендация
переносить слабые проверки в выпуск приложения без дополнительной валидации.
16-битная сумма не равна побайтному readback и не является криптографической
проверкой. Полный дамп flash штатным интерфейсом не восстановлен.

## 5. Что проверено исполнением исходного кода

`tools/emulate_keyboard_updater.py` загружает секции PE в память Unicorn x86,
вызывает семь указанных конструкторов и перехватывает USB на границе
`0x00428680 / 0x00428810`. Перехват возвращает только подготовленные ответы
из памяти. Непредусмотренное исполнение вне разрешённых функций прерывается;
Windows-процесс обновлятора, его GUI и реальные HID не создаются.

Проверено побайтное совпадение семи команд с собственной реализацией. Для
command5 исходный код дал ожидаемые статусы:

| Инъекция | AL |
|---|---:|
| SET_FEATURE завершился ошибкой | 0 |
| GET_FEATURE завершился ошибкой | 1 |
| Неправильный заголовок | 2 |
| Неправильный ACK | 4 |
| Правильный ответ | 5 |

Дополнительно модель воспроизвела полный поток8064 блоков и checksum67E7.
Это проверка кодека и модели, **не эмуляция ROM-загрузчика**. Электрические
параметры USB, реальная длительность erase, перенумерация и восстановление
после обрыва питания не проверялись.

## 6. Расширение на другие версии: что уже доказано

Нужно разделить три независимые возможности:

1. **Разбор пакетов.** Уже расширен: извлечение не привязано к одному SHA,
   размеру EXE, имени файла или PID. Поддерживаются PE32/PE32+, ресурсы и
   строгий Intel HEX. Два разных реальных пакета разобраны одним инструментом.
2. **Общий ISP-движок.** Код обеих исследованных версий одинаков. Один движок
   может работать с различными пакетами через профили MCU и платы. Для
   SN34F280 восстановлен и проверен кодек. Аппаратного испытания собственного
   transport пока нет.
3. **AJKS и функции Studio.** Изменённая прошивка и настройки платы требуют
   отдельной проверки каждой ревизии. Общий загрузчик этого не обеспечивает.

### Реальный тест переноса на8033 / 1.04

Активные образы1.36 и1.04 отличаются в79 969 байтах, 2429 непрерывных
диапазонах и172 блоках по512 байт. Исходный стек меняется с`20006D98` на
`20006F88`. У обоих есть нулевые области20000–263FF, однако пустота сама
по себе не доказывает, что их можно занимать или что RAM не используется.

Проверены36-байтные контексты шести реальных вставок AJKS:

| Назначение | Адрес в1.36 | Совпадений в1.04 |
|---|---:|---:|
| Вычисление подсветки | `0x1051C` | 0 |
| USB dispatcher | `0x10530` | 0 |
| Вращение энкодера | `0x57F4` | 0 |
| Нажатие энкодера1 | `0x10118` | 0 |
| Нажатие энкодера2 | `0x1013C` | 0 |
| Событие клавиши | `0x13D94` | 0 |

Это **не доказательство невозможности порта**: компилятор мог переместить
и изменить функции. Это доказательство, что существующий бинарный патч
не переносится простой заменой PID или сохранением старых адресов.
Новый `portability`-анализ сохраняет кандидаты и неоднозначности, но ничего
не патчит автоматически.

### Другие AK820MAX в материалах производителя

В трёх сохранённых снимках веб-драйвера имеется33 записи, всего11 разных
PID/каналов. Сырые профили с хешами источников сохранены отдельно.

| PID | Канал | Что позволяет заключить профиль |
|---|---|---|
| 8033, 8044, 8070 | USB | 82 клавиши, подсветка, макросы, Hall/advanced settings |
| 809B | USB | 82 клавиши; маршрут lighting отсутствует |
| 80A0 | USB | Наша исследованная ревизия; нет musicConfig |
| 80B0 | USB | Есть musicConfig; требует своего кодека возможностей |
| 80B1 | USB | Есть musicConfig другой версии |
| 80B9 | USB | Lightles, без маршрута lighting |
| FEFC, FEFD, FEFE | 2.4GHz | Отдельные радиопрофили; FEFC связан с исследованным80A0 |

Это снимки драйвера, а не испытанные здесь устройства. Из наличия одинаковой
раскладки82 клавиши нельзя вывести одинаковый MCU, GPIO, LED-index или радио.
Другие найденные пакеты AK820MAX имеют VID0416 или3151; их следует направлять
в отдельные backend, а не в SONiX ISP по сходству названия.

## 7. Как встроить результат в приложение

Сейчас `src/device_updates.rs` готовит копии и запускает OEM EXE; полностью
собственная установка ещё не подключена. `src/hardware.rs` выбирает только
80A0/FEFC и проверяет manufacturer/product, версии1.30/1.36.
`src/keyboard_memory.rs` дополнительно требует точный AJKS-протокол. Эти
ограничения нельзя ослабить одним общим условием «это AK820MAX».

Предлагаемая структура:

```text
PackageReader ──> FirmwareImage + доказательства происхождения
                         │
DeviceDiscovery ──> BoardProfile ──> CompatibilityResult
                         │
                 BootloaderProfile
                         │
                 NativeIspSession
                         │
           Re-enumeration + проверка результата

Отдельно: Capabilities для настроек, подсветки и AJKS.
```

BoardProfile связывает точную плату, приложение, MCU, допустимые образы и
варианты настроек. BootloaderProfile содержит USB-протокол, длины, геометрию,
ответы и временные ограничения. Capabilities позволяет показывать штатные
возможности и без AJKS: например, настройки и встроенные эффекты для
проверенной стоковой ревизии, даже если автономные программы ещё не портированы.

Для новой ревизии достаточно будет добавить проверенный профиль и, при
необходимости, backend/порт. Не потребуется копировать весь GUI или
подменять системные ID. При неизвестной ревизии приложение сможет собрать
диагностику и распознать пакет; запись и неподтверждённые функции не включаются.

Реестр `research/keyboard-updater/profiles.json` уже разделяет протокол и плату.
Для80A0 сопоставление со старым сохранённым USB-снимком проходит все8 проверок.
8033 внесён как исследовательская запись с неизвестным product и непроверенным
аппаратным путём. Утилита не превращает такую запись в разрешение записи.

### Что требуется до замены OEM в выпуске

- Реализовать Windows transport с эксклюзивным владением выбранным
  устройством, завершением анимаций/опроса и точным HID path. Повторное
  открытие handle после каждого пакета из OEM копировать необязательно.
- Проверить вход в ISP и связать появившееся7210 с тем же физическим
  устройством: container/location path, исчезновение предыдущего устройства,
  запрет неоднозначности при нескольких клавиатурах. Общий boot PID не
  содержит модель платы.
- На подтверждённой плате записать полный USB-транскрипт OEM и сверить его
  с восстановленным кодеком, таймингами, final status и ошибками Windows.
- Затем испытать собственную запись на той же ревизии с подготовленным
  способом восстановления. Не повторять вслепую erase или частично отправленный
  блок: в потоке нет номера, предотвращающего повторное продвижение адреса.
- Проверить результат после возврата в приложение: ожидаемая версия,
  служебная сигнатура AJKS, настройки, Hall-калибровка и сохранённые программы.

Для порта AJKS на другую firmware дополнительно нужны: scatter/RAM map,
позиции оригинальных вызовов и ABI, Hall→LED map, обработчик USB и его буферы,
flash API, занятость нулевых областей, энкодер и питание/радио.
Проверенный binary hash — ключ конкретного порта. Совпадение номера версии
без хеша недостаточно.

## 8. Инструменты и повторение исследования

Базовые команды требуют только Python и работают офлайн:

```powershell
python tools/keyboard_updater_lab.py inspect "пакет.exe" --out inspection.json
python tools/keyboard_updater_lab.py extract "пакет.exe" --out extracted
python tools/keyboard_updater_lab.py compare "пакет-A.exe" "пакет-B.exe" --out comparison.json
python tools/keyboard_updater_lab.py portability "база-1.36.exe" "другая-ревизия.exe" --out port.json
python tools/keyboard_updater_lab.py assess "пакет.exe" "снимок-клавиатуры.json" --out assessment.json
python -m unittest discover -s tests -p test_keyboard_updater_lab.py -v
```

`extract` записывает образ отдельно и сохраняет хеши/смещения ресурсов.
При конфликте с уже существующим файлом доказательств он прекращает работу.
HEX проверяется по каждой записи: длина, checksum, EOF, перекрытия, базовые
адреса. Проверяются выходы за PE-секции, неоднозначные ресурсы, пути ZIP,
дубликаты имён и лимит распаковки. Нет функций запуска EXE или записи в HID.

Собственный кодек — `tools/sonix_isp.py`. DownloadModel — модель
последовательности и ошибок, не готовый аппаратный flasher. Она специально
ограничена проверенным CS0-путём SN34F280, без смены security и неопределённых
повторов. Восстановленные другие семейства пока представлены данными таблицы.

Расширенные воспроизводимые команды из исходного проекта:

```powershell
python tools/decompile_keyboard_updater.py
python tools/decompile_keyboard_updater.py --details
python tools/emulate_keyboard_updater.py
python tools/audit_keyboard_updater.py
```

Для декомпиляции используются локальные Ghidra/JDK из`.tools`, для x86-эмуляции —
Unicorn из`.tools/py-research`. Они не нужны для просмотра готового отчёта или
разбора нового EXE базовой утилитой. После первого анализа снова запускать
исходный прошивальщик не требуется: C-экспорты, протокол, таблицы, хеши и
проверки сохранены.
