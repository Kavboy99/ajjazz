# Кастомизация прошивки дока AJ159 APEX

**Текущая ветка:** RGB отложен пользователем. Для экрана создан кандидат AJSC v1
с живыми CPU/RAM и настройками из AJAZZ Studio0.14.0. Исполняемый код проверен
в ограниченной эмуляции и установлен на ID1759: AJSC и живые CPU/RAM подтверждены
ответами устройства. Вид панели ожидает проверки пользователем; физическое
восстановление ещё не проверено.
См. [DOCK-SCREEN-TELEMETRY.md](DOCK-SCREEN-TELEMETRY.md). Утверждения ниже о том,
что никакого собственного образа не создано, относятся к предыдущему этапу.

**Обновление 23 октября:** из нового письма AJAZZ полностью извлечены отдельные
USB/RF/экранные образы. Старые записи об отсутствии файла ниже исторические.
Свежие идентификаторы, проверка кнопки, воспроизведение распаковки и границы
готовности своей прошивки: [SUPPORT-PACKAGE-20261023.md](SUPPORT-PACKAGE-20261023.md).

Приоритет уточнён пользователем: экран и подсветка дока. Получение прошивки самой мыши не является предварительным условием исследования и доработки этих функций. Док содержит также USB-приёмник; расположение экранного, RGB и радиокода по физическим контроллерам пока не установлено.

Целевой док: USB3151:5007, ID1759, экран OLEDV104. Физический ID подтверждён собственной командой дока F1, в том числе повторно22 октября.8F относится к мыши и не заменяет F1. Кастомный образ для дока пока не создан. Настоящие отдельные экранные образы других устройств получены как материал для сравнения; они не назначены совместимыми.

## Что должно работать на доке

- Редактируемые страницы экрана: часы, изображения, анимации и доступные сведения о мыши; выбор порядка и времени показа.
- Собственные эффекты RGB, палитры, скорость и яркость; адресация отдельных светодиодов после определения их физической схемы.
- Сохранение конфигурации и воспроизведение локальных сцен без постоянной передачи кадров с ПК.
- Настройка через AJAZZ Studio, сохранение USB-ввода, радиосвязи и штатной зарядки.

Число контроллеров, модель LED, количество диодов и общность их управления с экраном не предполагаются по внешнему виду. Телеметрия ПК потребует работающего источника данных на ПК; часы и локальные анимации должны исполняться самостоятельно.

## Разработка переносимого ядра

Добавлен самостоятельный `firmware/dock-core` на Rust `no_std`: вычисляемые на MCU RGB-слои, маски LED, четыре пресета, расписание страниц, часы и сохранённые последовательности кадров. Рендер построчный, без полного framebuffer и без allocator. Временные фазы слоёв рассчитываются один раз за кадр. Подробный контракт аппаратного порта и границы: [README ядра](../firmware/dock-core/README.md).

`scripts/check-dock-core.ps1 -Embedded` прошёл:18 проверок, clippy с `-D warnings`, fmt и release-сборка библиотеки для `thumbv6m-none-eabi`. Это проверка переносимого кода для Cortex-M0, **не идентификация MCU дока, не измерение физической частоты и не готовый flashable BIN**. Нет драйвера платы, загрузчика, USB-команд и реализации flash-хранилища. В AJAZZ Studio0.13.2 эта библиотека пока не включена, аппаратные функции приложения не объявлены расширенными.

Добавлен `config::Configuration`: единый для будущего MCU-порта и приложения формат AJDC v1, до236 байт. Включает частоту, яркость, слои, маски, палитры, страницы и параметры анимаций. Декодер проверяет длины, версию, CRC32, enum, диапазоны и нулевые резервные поля; не изменяет работающую конфигурацию. Проверены все усечения и1888 одиночных битовых повреждений максимального пакета, семантически неверные пакеты с верным CRC и ограниченный генеративный набор. Это **не протокол штатного дока и не реализация сохранения во flash**. Спецификация: [CONFIGURATION.md](../firmware/dock-core/CONFIGURATION.md).

Дополнительный путь22 октября: производственная MouseDeviceTool V0.0.007 из подтверждённого каталога Panchip, `https://wiki.panchip.com/download/3090/`. Новая утилита `tools/fetch_panchip_mouse_device.py` проверяет границы HTTP Range, размер ZIP, имя/размер участника и CRC ZIP до сохранения PE. Две попытки получения завершились сетевыми тайм-аутами (чтение, затем TLS handshake); EXE не получен и его команды **не разобраны**. На док команды не посылались. Запуск этой утилиты не равнозначен извлечению прошивки устройства.

## Разбор точного профиля дока

В установленном renderer с SHA-256 `8b44162b7f8c2d6640b7ec38640b5441b5b48b63175d2996fdce3130e5c4bb01` фабрика `common_dangle` создаёт `qpa`. В этом профиле `getOLEDversion` использует AD; `upgrade` и `setLightSetting` возвращают false. Это ограничение реализации штатного профиля, а не доказательство отсутствия аппаратной возможности обновления или RGB-контроля.

`getTFTLCDDataRGBImg` с A5/A9 передаёт длину, слот, число кадров, задержку и прямоугольник, затем ждёт status1. Пиксельных данных из ответа не извлекает: это подготовка загрузки, не чтение flash. `setTFTLCDDataRGBImg` отправляет25/29 с56-байтовыми частями. `setFlashChipErase` посылает AC и ожидает `AC AA AA 55 55`; эту команду нельзя использовать как пассивный GET. Код сохранён в `research/local/mouse-firmware-20261021/dock-qpa-context.js`.

В родственном классе `flashUpgrade` команда B2 (`GETTFTFLASHDATA`) проверяет готовность к записи, после чего следуют части firmware. Название не доказывает функцию выгрузки кода. На физический док эти исследовательские команды не отправлялись.

## Первая подписанная часть приёмника и код в RAM

Прежний экспорт Ghidra намеренно пропускал10000–30200. Это не был полный разбор обеих подписанных частей. Для связанного приёмника теперь отдельно экспортирован компонент10000: таблица из17 указателей по10208–1024C, следующие за ней переходники в RAM и их назначения.

В scatter-таблице27DC4 первая запись задаёт прямое копирование27DF4 →2000C800 длиной2B28 (11048 байт), процедурой10A9A. Оригинальная процедура исполнена в Unicorn с синтетической RAM и read/execute flash;2762 записи слова строго в указанное назначение, полное сравнение байтов успешно. Это **не запуск контроллера или физического дока**. Проверка: `tools/verify_controller_ram_copy.py`; отчёт: `controller-ram-copy-validation.json`.

Код размещён по рабочим адресам только в проекте Ghidra. Вторую scatter-запись с распаковкой и третью с обнулением не подменяли предположительным memcpy. Экспорт760 функций: `ghidra/dock-MV303-DV233-reference.bin.controller.{c,tsv}`. Воспроизведение: `python tools/decompile_mouse_reference.py --component dock --controller`. Остаются предупреждения декомпилятора; F1/F7 и чтение кода экрана в этой части пока не локализованы.

В [официальном описании Panchip](https://docs.panchip.com/pan1080dk-doc/latest/docs-zdk/03_samples/solutions_hid/hs_mult_ms.html) отдельно выделен фиксированный BLE controller около120КБ. Наличие BLE-подобных функций в первом компоненте согласуется с этим описанием, но не доказывает, что это USB/RGB-контроллер физического дока.

## Отдельный высокоскоростной USB-компонент

В [официальном описании HS Common Dongle](https://docs.panchip.com/pan1080dk-doc/latest/docs-zdk/03_samples/solutions_hid/hs_mult_common_dongle.html) PAN108x и высокоскоростной USB-чип программируются отдельно; данные между ними передаются по SPI. В [старом описании 4K-приёмника](https://docs.panchip.com/pan1080dk-doc/1.0.2/docs-zdk/03_samples/solutions/multimode_mouse_dongle_4k.html) USB-компонент назван CH32V30x и указан отдельный проект `CH32_CODE/EXAM/USB/USBHS/DEVICE/CompatibilityHID`.

Это подтверждает архитектуру справочного решения, **не маркировку физического дока1759**. Полученные PAN-образы нельзя считать полным комплектом прошивки всех компонентов дока. Поиск USB-обработчиков F1/F7, загрузки экрана и RGB следует продолжать также в отдельном USB-компоненте. Справочные CH32/PAN образы не назначаются совместимыми без установления платы и восстановления.

Конфигурация связанного обновлятора различает USB3151:5007 (`DANGLE4K`, `DANGLE4KRF`) и3151:4027 (`DANGLE1K`). Эти строки сохранены с SHA исходного JSON в `usb-bridge-route-reference.json`. Они подтверждают разные маршруты ПО, но не конкретную модель USB-чипа. В новых версиях SDK также упоминается AT32; нельзя автоматически назначать доку CH32 по старому справочному проекту.

Вокруг ранее неразобранных ссылок `dangle4k.rs` дополнительно восстановлены7 функций:728E20,729680,729DE0,729F30,72A080,72AC30,72B800. Экспорт `ghidra-updater/dock-updater-usb-bridge.{c,tsv}`, воспроизведение `python tools/decompile_dock_updater.py --usb-bridge-candidates`. Предупреждения восстановления switch/адресов остаются; это не полная декомпиляция обновлятора.

В USB-ветке72A080 видна проверка размера не более153600 байт;72AC30 передаёт рабочее смещение5000 следующей процедуре. В PE проверены фактические литералы входа USB-компонента `7F 55 AA 55 AA 00 00 00`, опроса `09 15` и отдельного входа радиокомпонента `F8 55 AA 55 AA 00 00 82`. Строка log для7F отличается от фактического литерала; приоритет у байтов файла. Эти команды **не отправлялись** доку. Отчёт `usb-bridge-update-path-audit.json`. Предел размера и смещение не доказывают ни модель MCU, ни совместимость образа.

Из официального SDK430 получен `Panchip Tools Directory V0.0.016.exe`, SHA `ea051e86c92faf94e053c3d403302cc8c51778e00c8968429b344e9ec83d2cd6`. Утилита не запускалась: `tools/inspect_panchip_tool_catalog.py` извлекает константы трёх Python-модулей статическим разбором PyInstaller/xdis. Точные публичные ссылки сохранены в `sdk-131-tool-directory/verified-catalog-urls.json`. Отдельный проект высокоскоростного USB-чипа в этом каталоге не найден. Пакеты DFU/MouseDevice/ProDriver проиндексированы отдельно; исходный проект мостового MCU пока не получен.

Затем с официального download3023 извлечён `PanchipDFUTool V0.2.001.exe`,37091968 байт, SHA `49f59c1e5fa1597ae049401f75ed6328168910235f938622f9d48fc2327e1c0f`. Проверка `tools/inspect_panchip_dfu.py` статически разбирает четыре модуля: `dfu_usb_com`, `dfu_program`, `dfu_trans_dev_program`, `dfu_face_dlg`. Код программы не импортируется и не запускается. Ресурсы содержат руководства и шаблон экспортируемого EXE, отдельного BIN/HEX нет. Два совпадения MCUboot magic в шаблоне — операнды инструкции `cmp eax, 0x96f3b83d` в `.text`, а не заголовки прошивок. Отчёт `sdk-131-tool-directory/dfu-static/audit.json`.

В просмотренных command builders есть чтение версии, типа и CID, проверка образа и команды загрузки/завершения/входа в обновление. Процедура выгрузки произвольного исполняемого кода в этих модулях не найдена. `getProgramDatas` работает с уже загруженным файлом ПК, а `read_datas` читает ответы HID; названия не означают чтение flash устройства. Это ограниченный отрицательный результат для разобранных модулей, не доказательство отсутствия любых ROM/debug-режимов.

Штатный Panchip-протокол использует Report0A и Interrupt OUT. Сохранённые дескрипторы нашего дока показывают другой транспорт: три HID-интерфейса только с IN endpoints и управление через Feature. Поэтому команды справочной утилиты нельзя считать автоматически поддерживаемыми доком. В этой ветке исследования они не отправлялись. Получение точного образа дока или подтверждённого чтения его кода остаётся незавершённым.

## Проверка кнопки отложена

Длинная пассивная запись22 октября завершилась по лимиту1800 секунд с0 Input-отчётов, без Output/Feature. Пользователь находится вне дома и не нажимал кнопку в рамках опыта. Поэтому аппаратный опыт **не выполнен**, результат не говорит, передаётся ли нажатие по USB. Отчёт `dock-passive-rgb-button-long-20261022.json`; активной записи больше нет. До возвращения пользователя работа ограничена анализом файлов и источников.

## Дополнительные пути получения образа

Найден [описанный авторами MonsGeek-проекта способ](https://github.com/echtzeit-solutions/monsgeek-akko-linux/blob/79c45f11dcc0fdd24d6075a0f30f5dabbc748c9b/firmwares/2949-v407/UPGRADE_DUMMY.md) перехвата обновления через UHID/Wine и формат обёртки `x1`: первый байт raw-DEFLATE сохраняется, продолжение берётся с203-го байта. Контрольный `x1` с зафиксированным SHA декодирован, затем `tools/audit_updater_x1.py` проверил32954 кандидата в неисполняемых секциях четырёх связанных обновляторов. Совпадений выбранных признаков образа нет. Это ограниченная эвристика, не доказательство отсутствия любых других упаковок. Контрольный поток не содержит финального EOF, поэтому его не объявляли целевым проверенным образом. Отчёт `updater-x1-format-audit.json`.

В том же проекте опубликован полный PAN108-дамп, но [авторы получили его через SWD](https://github.com/echtzeit-solutions/monsgeek-akko-linux/blob/79c45f11dcc0fdd24d6075a0f30f5dabbc748c9b/docs/HARDWARE.md), с другой платы. Это подтверждает внешний аппаратный путь для их устройства, не чтение нашего дока по USB. Чужой дамп не устанавливался.

Пакет с точным названием AJ159 APEX найден на сервере EPOMAKER: `https://orders.epomaker.com/software/AJ159_APEX_PAW3950_Win_driver.zip`,157121017 байт. Центральный каталог ZIP прочитан через HTTP Range. Состав: установщик2.1.94, iot_driver, VC++ Runtime и два текстовых файла; самостоятельного обновлятора/образа в архиве нет. Индекс `research/vendor/panchip-reference/apex-official-package/index.json`. Большой размер пакета обусловлен также VC++ Runtime. Более старые точные файлы из исторического каталога по проверенным downloader URL дали404, source URL — timeout; Wayback для трёх проверенных file URL не вернул захватов. Отчёты `old-apex-*-probes.json`, `exact-apex-package-wayback-captures.json`. Нельзя заключать, что старый пакет содержал прошивку, по одному размеру.

## Что ещё требуется установить

1. Точный экранный/USB-образ дока1759 либо подтверждённое чтение его кода и возможность восстановления.
2. Связь экранного контроллера с RGB: общий ли MCU, способ вывода сигнала, таблица LED и обработчик нижней кнопки.
3. Границы изменяемого компонента, чтобы сохранить код USB-приёмника и радиоданные.

Получение точной прошивки мыши1755 больше не числится обязательным шагом для этой ветки. Препятствие — идентификация и восстановление экранного/RGB-компонента дока. Образы Keydous и EPOMAKER не прошивались на подключённые устройства.
